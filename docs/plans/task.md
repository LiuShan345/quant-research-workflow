# 任务定义：A 股月度截面动量策略的可重复研究与监测工作流

> 文档版本：v0.1（任务定义草稿）
> 对应期末作业第 1 部分：明确一项内容充实、重复执行的任务

## 1. 一句话目标

把一个量化研究员"从提出交易想法到产出可核验回测结论、再到每月持续跟踪"的完整研究过程，设计成一条**多阶段、保留状态、可重复评估、能从中断恢复**的智能体工作流。

## 2. 目标用户与使用场景

- **目标用户**：买方量化研究员（个人或小团队），需要反复提出、检验和跟踪股票策略。
- **典型场景**：研究员有一个"动量效应"的想法，希望系统每月自动用最新数据重跑研究、核验结果、更新报告，并在指标异常时提醒人工介入；研究员本人保留所有重大决策的批准权。

## 3. 研究假设（待检验的想法）

- **假设**：A 股中过去一段时间（回看期 J 个月）涨幅领先的股票，在未来 1 个月（持有期）倾向于继续跑赢，即存在**截面动量效应**。
- **策略规则（初版）**：每月末计算每只股票过去 J 个月的累计收益率，按从高到低排序，等权买入排名前 K 只，持有 1 个月后按同样规则调仓。
- 初始参数：`lookback J = 6 个月`、`持仓数 K = 3`；参数是否稳健由后续稳健性检验回答。
- 上述假设与参数都**不是结论**，只是待检验对象；研究验收通过不等于策略能盈利，更不构成下单授权。

## 4. 现有（人工）流程与痛点

人工做法通常是：研究员临时写脚本下载数据、在笔记本里拼回测、手动改参数、把结果贴进报告。痛点包括：

1. **不可复现**：数字来自哪个数据版本、哪段脚本，事后说不清。
2. **容易"穿越"**：不小心用了调仓时点还不知道的信息（未来信息泄露），回测虚高。
3. **断点丢失**：跑了一半中断，已完成的步骤要重来。
4. **无版本管理**：改了参数或提示词后效果变差，无法干净地退回上一版。
5. **缺少独立核验**：写代码的人自己检查，容易犯同样的错误。

## 5. 工作流阶段与依赖关系

工作流分为 7 个阶段，后一阶段必须等前一阶段通过检查关卡后才能开始：

| 阶段 | 主要工作 | 关键输入 | 产物 | 前置依赖 |
|---|---|---|---|---|
| S1 假设登记 | 登记想法、参数、验收标准、信息截止时点 | 研究员的自然语言想法 | idea.json | 无 |
| S2 数据准备 | 生成/拉取带日期的价格数据，做质量检查并固化快照 | 股票池、日期范围 | 数据快照 + 哈希 | S1 |
| S3 因子/信号构建 | 只用截至每个调仓日已可得的数据计算动量信号 | S2 快照 | 信号表（含信号可用时间） | S2 |
| S4 回测 | 信号可用之后才允许交易，扣除交易成本，遵守 T+1 | S2、S3 | 回测结果、净值、交易记录 | S3 |
| S5 稳健性检验 | 改变 J/K、扰动未来价格、压力测试成本，检查结论是否稳定 | S4 候选策略 | 稳健性报告 | S4 |
| S6 组合构建 | 等权配置、检查持仓与限额，形成待批准的交易清单 | S4、S5 | 候选组合清单 | S5 |
| S7 持续监测 | 每月用新数据重跑，监测指标漂移与共同风险，触发报警 | 新数据/新案例 | 监测报告、告警 | S6（循环） |

- **依赖关系**：S1→S2→S3→S4→S5→S6 为前向链；任一阶段检查不通过，沿"修复边"退回对应阶段修订，因此完整工作流包含循环。
- **确定性计算**：数据质量检查、动量排序、收益/夏普比率/最大回撤等所有数值计算，由 Python 确定性代码完成；智能体只负责理解任务、生成代码和解读结果，不做心算。

## 6. 重复触发条件

- **定时触发**：每月最后一个交易日（调仓日）自动启动一次新案例，用最新数据重跑全流程。
- **事件触发**：出现新的研究想法、数据源更新、或监测阶段报告异常时，触发对应阶段或新案例。
- **输入版本变化**：当输入数据版本变化（如数据被修正）时，启动新案例并重建依赖该数据的下游产物。

## 7. 输入、允许来源与信息截止时点

- **默认输入**：仓库自带的**合成数据**——10 只虚构股票、约 3 年的带日期价格序列（位于 `tests/fixtures/`），保证任何人无需账号即可复现，且不含真实客户信息。
- **允许来源**：默认仅使用本地合成 fixture；数据访问层预留接口，未来可切换到公开数据源（如 AKShare）或校内数据库（如 CSMAR），但切换需在配置中显式声明并经人工批准。
- **信息截止时点**：每个数据快照都写明 `as_of` 截止时点；**任何阶段只能使用 `as_of` 不晚于当前调仓日的信息**，这是防止未来信息泄露的硬性约束。

## 8. 工作产出

1. 带日期、带哈希的数据快照与信号表；
2. 可复现的回测输出：净值曲线、交易记录、年化收益、夏普比率、最大回撤、换手率；
3. 稳健性检验报告与监测报告；
4. 待人工批准的候选交易清单；
5. 完整的核验记录、问题项台账、版本与批准记录。

## 9. 验收标准

一个候选策略只有同时满足以下条件才能被标记为"研究验收通过（ACCEPTED）"：

1. 所有必要的代码检查关卡（数据质量、时序、数值、成本、限额）全部通过；
2. 不存在未解决的问题项，且问题项的关闭必须由独立 Critic 核验；
3. 同一候选策略**连续两轮**通过 Critic 的完整审查（策略一旦改动，连续计数清零重算）；
4. 时序检查证明：所有交易都发生在信号实际可用之后，无未来信息泄露；
5. 全部产物均有数据来源与哈希，可由他人独立重跑得到相同数值。

再次强调：研究验收通过**既不证明策略盈利，也不构成任何交易授权**。

## 10. 为什么需要持久化工作流，而不是一次性脚本

本任务不是"跑一次出一张表"，而是一项长期、重复、强审计的研究活动，一次性脚本无法满足：

1. **长期重复执行**：每月调仓、新想法和新数据都会触发重跑，需要固定的调度与触发机制；
2. **中断恢复**：长流程可能因超时、网络或人工暂停而中断，需要检查点让系统只重做未完成部分、不重复已完成操作；
3. **留痕与审计**：金融决策需要保留"当时知道什么、算了什么、谁批准了什么"的完整证据链；
4. **版本演进与回滚**：提示词、技能、代码和参数会持续改进，必须对照固定基线评估、按版本管理并能回滚；
5. **授权边界与人工关口**：重大操作前必须人工批准，且要区分研究验收、版本批准与资金授权。

这些需求依赖持久化的状态、检查点和控制器，而不是一段跑完即结束的脚本。
